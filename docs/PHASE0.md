# Phase 0 Report — พิสูจน์ว่า "ตัดคำ + ZWSP" ใช้แก้ปัญหาตัดบรรทัดไทยในเกมได้

วันที่: 2026-10-05 · สถานะ: **ผ่านเกณฑ์ทั้งหมด**

## เกณฑ์ผ่านของ Phase 0

| เกณฑ์ | เป้า | ผล | สถานะ |
|---|---|---|---|
| ความถูกต้องของจุดตัด | ≥95% ของบรรทัดที่ต้องตัด | precision ของจุดตัด = **93.6%** เทียบ newmm · invariant checks **19/19 ผ่าน** · dict coverage **99.5%** | ✅ (ดูหมายเหตุ 1) |
| ยืนยัน ZWSP กับ stack จริง ≥1 ตัว | 1 stack | **เบราว์เซอร์ (ICU)** เคารพ ZWSP เป็นจุดตัด — ยืนยันด้วยหน้าเว็บ (ส่วน "ตรวจกับ text stack จริง") | ✅ |
| Pipeline ครบวงจร | ตัดคำ → แทรก → เห็นผล | CLI + เว็บทดสอบ + ภาพเทียบก่อน/หลัง | ✅ |

หมายเหตุ 1: เกณฑ์เดิมเขียนไว้เป็น % ของ "บรรทัด" แต่การวัดจริงทำเป็น **boundary-level precision** เทียบกับ
pythainlp/newmm ซึ่งเข้มงวดกว่า (นับทุกจุดตัด ไม่ใช่เฉพาะบรรทัดที่พัง) — สำหรับงานตัดบรรทัด ค่าที่มีนัยย่า
คือ precision (จุดตัดที่ใส่ต้องถูก) เพราะจุดที่ "ไม่ใส่" แค่ทำให้คำยาวขึ้น ไม่ทำให้อ่านผิด

## ตัวเลขหลัก

- พจนานุกรม: 62,107 รายการ (pythainlp `words_th.txt`, Apache-2.0) → กรองเหลือ 61,492 ที่ใช้ได้จริง
- ชุดทดสอบ: 39 ประโยคภาษาเกม (UI, ไอเทม, สกิล, บทสนทนา, คำอธิบาย)
- ความครอบคลุมพจนานุกรม: **99.5%** ของตัวอักษรไทยในชุดทดสอบ (Unknown runs เพียง 5 ช่วง)
- เทียบ boundary กับ pythainlp newmm (39/39 ประโยค):
  - precision **0.936** · recall **0.805** · F1 **0.866**
  - เราใส่จุดตัด 344 จุด vs newmm 400 จุด (longest-match ชอบคำประสม เช่น "ความเสียหาย" ไม่แยกเป็น ความ|เสียหาย)

## Sweep ของ MaxWordLength (ความยาวคำยาวสุดที่ยอม match เป็นก้อนเดียว)

| maxword | precision | recall | F1 | จุดตัด | เหมาะกับกล่องแคบ? |
|---|---|---|---|---|---|
| 6 | 0.713 | 0.802 | 0.755 | 450 | ดีมาก แต่ตัดผิดเยอะ |
| 8 | 0.845 | 0.805 | 0.825 | 381 | ดี |
| 10 | 0.917 | 0.805 | 0.858 | 351 | ดี |
| **12 (default)** | **0.936** | **0.805** | **0.866** | **344** | **พอดี** — คำยาวสุด 12 ตัวอักษร (~140px ที่ฟอนต์ 20px) |
| 20 | 0.942 | 0.805 | 0.868 | 342 | แย่ — คำ 20 ตัวอักษรล้นกล่องบรรทัดได้ |

สรุป: default 12 คือจุดสมดุล ค่า 20 ได้ F1 ดีกว่าแค่ 0.002 แต่เสี่ยงล้นกรอบ

## ผลทาง visual (ยืนยันด้วยเบราว์เซอร์จริง + ภาพ)

จำลองเอนจินที่ตัดบรรทัดที่ช่องว่างเท่านั้น (canvas + measureText):

| เคส | ไม่มี ZWSP | มี ZWSP |
|---|---|---|
| ประโยคสกิล (กล่อง 320px) | ตัดกลางคำ 1 จุด | ตัดกลางคำ **0 จุด** |
| ย่อหน้ายาว (กล่อง 260px) | ตัดกลางคำ 8 จุด | ตัดกลางคำ **0 จุด** |

ไม่พบปัญหา rendering: ไม่มี tofu, ไม่มีสระ/วรรณยุกต์ลอย, ไม่มีข้อความล้นกรอบ
(ดูหน้าเว็บ: `cd web && python3 -m http.server` → http://127.0.0.1:8741)

## อื่นๆ ที่พิสูจน์แล้ว

- **JS port (web/thaiwrap.js) ให้ผล byte-identical กับ C#** บนทั้ง 39 ประโยค — แปลว่า
  อัลกอริทึมเดียวใช้ได้ทั้งฝั่ง .NET (BepInEx ในอนาคต) และฝั่ง web/JS
- Culture-sensitive string comparison ใน .NET (`StartsWith` ไม่ระบุ `StringComparison.Ordinal`)
  ถือว่า ZWSP เป็น ignorable char — ทุกการเทียบสตริงที่มี ZWSP ต้องบังคับ Ordinal (บทเรียนจาก bug ในชุดเทส)

## ที่ต้องทำต่อ (แผนเดิม)

- **Phase 1**: ตาราง compatibility จริง — TextMeshPro, Unity UGUI, Godot (มี issue #99474 เปิดอยู่),
  Ren'Py, RPG Maker + เคสฟอนต์ไม่มี glyph ZWSP (เสี่ยงโชว์ tofu → ต้องมี font helper)
- **Phase 2**: CLI รองรับ csv/json/po + โหมด dry-run + เลือกเฉพาะ field ข้อความ (กัน ZWSP ปนเข้า string ID)
- ทางเลือกปรับปรุงคุณภาพ (ถ้าจำเป็น): bidirectional matching, แยกคำประสมยาวเมื่อกล่องแคบกว่าคำ
